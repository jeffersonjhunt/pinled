# Firmware Requirements — `pinled` v2

Requirement IDs are stable; status is `MVP` (first working build), `v1`
(feature-complete for release), or `future`. "SHALL" = required, "SHOULD" =
desired, "MAY" = optional.

## 1. Sensing / scan

| ID | Req | Status |
|---|---|---|
| FR-SCAN-1 | The system SHALL scan lamp channels via daisy-chained 74x165 parallel-in / serial-out shift registers, two per module, reading channel state as one serial stream. | MVP |
| FR-SCAN-2 | The system SHALL support 16 channels per module (2× '165, the second feeding the first's `SER`). | MVP |
| FR-SCAN-3 | The system SHALL support 1..8 identical, unaddressed modules chained on a 5-conductor harness. `CLK` and `/PL` are bussed to every module; `DATA` is point-to-point, `QH` → `SER`, one push-pull driver per hop. See `CHAINING.md`. | MVP |
| FR-SCAN-4 | A scan frame SHALL raise `/PL` — capturing every channel in the chain on that one edge — then issue **16*N** clocks, sampling `DATA` in the middle of each bit cell. Stream bit *i* (MSB-first) SHALL be channel *i*; no samples are discarded. Any module count 1..8 SHALL be legal. | MVP |
| FR-SCAN-5 | Per-channel raw sample rate SHALL be configurable and default to 10 kHz. | MVP |
| FR-SCAN-6 | Channel active polarity SHALL be configurable, defaulting to **active-high** (FET + inverting Schmitt trigger = non-inverting front end). | MVP |
| FR-SCAN-7 | The clock burst SHOULD be generated by SPI + DMA (`SCLK`=`CLK`, `MISO`=`DATA`, mode 2, receive-only). `/PL` SHOULD be driven from `CS` with positive polarity, so the line is low between transactions (loading) and high during one (shifting) and the capture instant is hardware-timed. | MVP |
| FR-SCAN-8 | Sampling SHALL be paced to a fixed configured rate independent of channel count. The SPI transaction cadence provides this directly; no separate pacing timer is required. | MVP |
| FR-SCAN-9 | The driver SHALL measure actual frame time at boot, clamp the configured rate to what the hardware sustains at ≤ 60% core occupancy, and publish the resulting rate as the authoritative Fs for all downstream time-constant math. | MVP |
| FR-SCAN-10 | A frame SHALL be a **single** SPI transaction. The driver's fixed per-transaction overhead (~17 µs measured, `TIMING.md` §2.4) is paid once per frame, never once per module. | MVP |
| FR-SCAN-11 | A wrong `num_modules` SHALL degrade benignly in both directions: too high reads hard zeros from the chain terminator, too low leaves trailing modules unread. Neither SHALL shift or misalign the channels that are present. | MVP |

## 2. Filament (brightness reconstruction)

| ID | Req | Status |
|---|---|---|
| FR-FIL-1 | Each channel SHALL run a leaky integrator emulating an incandescent filament's thermal response. | MVP |
| FR-FIL-2 | Attack (rise) and decay (fall) time constants SHALL be independently configurable, default ~20–50 ms. | MVP |
| FR-FIL-3 | The integrator SHALL accept normalized duty (0..1) or per-sample boolean and output brightness 0..255. | MVP |
| FR-FIL-4 | A configurable output gamma/curve SHALL map integrator level → LED PWM to match perceived bulb response. | v1 |
| FR-FIL-5 | Math SHALL be fixed-point (no float in the hot loop) and run for ≥ 64 channels within frame budget. | MVP |

## 3. Auto-profiling

| ID | Req | Status |
|---|---|---|
| FR-PROF-1 | The system SHALL classify each channel as STEADY / MATRIX / AC_STEADY / AC_DIMMED / OFF from observed transitions. | v1 |
| FR-PROF-2 | Profiling SHALL run at boot and be re-armable at runtime. | v1 |
| FR-PROF-3 | Classifier output `{class, duty_norm, period_est, confidence}` SHALL seed each channel's integrator gain/attack/decay. | v1 |
| FR-PROF-4 | A machine profile MAY override or lock per-channel class/params. | v1 |
| FR-PROF-5 | The observation window SHALL be specified in milliseconds (default 500 ms–1 s) and the frame count derived from the measured Fs, so the window spans several AC and matrix periods at any channel count. | v1 |
| FR-PROF-6 | The classifier SHOULD be robust to correlated false edges from solenoid-induced ground bounce (e.g. discard frames in which an implausible fraction of channels transition together). | v1 |

## 4. LED output / mapping

| ID | Req | Status |
|---|---|---|
| FR-LED-1 | The system SHALL drive a WS2812B/SK6812 string from a single GPIO (RMT). | MVP |
| FR-LED-2 | A mapping table SHALL relate sensed channel → LED index(es) + base color. | MVP |
| FR-LED-3 | LED frame/refresh rate SHALL be configurable (default 60–120 Hz) and decoupled from scan rate. | MVP |
| FR-LED-4 | Per-lamp color/tint (e.g. warm-white for GI, colored inserts) SHALL be configurable. | v1 |
| FR-LED-5 | The renderer SHOULD gamma-correct and dither low levels to avoid visible stepping. | v1 |
| FR-LED-6 | The renderer SHALL build one frame and issue a single strip transmit per refresh, not one transmit per channel. | MVP |
| FR-LED-7 | A global brightness/current cap SHALL bound worst-case LED draw (~6 A at 128 LEDs full-on). | v1 |
| FR-LED-8 | `led_count` × per-LED transmit time SHALL be validated against `refresh_hz` at boot and the refresh rate clamped if it does not fit. | MVP |

## 5. Configuration / profiles

| ID | Req | Status |
|---|---|---|
| FR-CFG-1 | Machine profiles (channel map, colors, integrator params, profiler locks) SHALL persist in NVS. | v1 |
| FR-CFG-2 | Build-time defaults SHALL be settable via Kconfig (`idf.py menuconfig`). | MVP |
| FR-CFG-3 | Profiles SHOULD be loadable/exportable as a human-readable text/JSON blob. | future |
| FR-CFG-4 | The system SHALL boot to sane defaults with no stored profile. | MVP |

## 6. Diagnostics

Bring-up aids. All default to off/normal so production behavior is unchanged;
see `BRINGUP.md` for how they are used together.

| ID | Req | Status |
|---|---|---|
| FR-DIAG-1 | The firmware SHALL be able to log the raw pre-filament channel bitmap plus a sticky per-channel "has been seen both high and low" flag (`PINLED_SCAN_DEBUG`), isolating the sense bus from the filament model and the LED string. | MVP |
| FR-DIAG-2 | The firmware SHALL be able to advance the scan at a human-visible rate (`PINLED_SCAN_STEP_MS`), logging each bit index, the channel it maps to, and the level read. The chain holds no analog state, so it can be clocked arbitrarily slowly. It SHALL re-assert `/PL` between steps rather than walking one frozen snapshot, so an input toggled part-way through the walk is still visible. | MVP |
| FR-DIAG-3 | The firmware SHALL be able to park the chain on a single channel indefinitely (`PINLED_SCAN_HOLD_CH`): snapshot, clock exactly *k* times, stop. `DATA` then holds channel *k* as a static DC level a meter can read. Holding `/PL` **low** instead is the useful special case — the registers stay transparent, so `DATA` tracks module 1 channel 0 *live*, following a button in real time. | MVP |
| FR-DIAG-4 | Modes that take ownership of the chain SHALL suppress `scan_task` rather than race it, and SHALL say so in the log. | MVP |

## 7. Non-functional

| ID | Req | Status |
|---|---|---|
| NFR-1 | Target ESP-IDF **5.5.x**, IDF_TARGET `esp32s3`. Reference board is the Adafruit QT Py ESP32-S3; the ESP32-S3-DevKitC-1 is a supported bring-up board (same GPIO numbers, see `HARDWARE.md`). Neither is the shipping form factor — the product places a bare S3 on the mainboard. | MVP |
| NFR-2 | Reusable logic (scan, filament, profiler) SHALL be ESP-IDF components with public headers under `include/`. | MVP |
| NFR-3 | Code style SHALL follow the existing repos: C++, `ooe::pinled` namespace, Doxygen headers, `esp_err_t` returns, `ESP_LOG*` with per-file `TAG`, `ESP_ERROR_CHECK`. | MVP |
| NFR-4 | No dynamic allocation in per-sample / per-frame hot paths. | v1 |
| NFR-5 | BOM target ≤ ~$25/strip; original ESP32-class MCU. | v1 |
| NFR-6 | License MIT; third-party attributions retained under `licenses/`. | MVP |
| NFR-7 | The CPU SHALL run at 240 MHz (`CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ_240`). Every figure in `TIMING.md` §2 derives from it and the IDF default for `esp32s3` is 160 MHz, which inflates the frame budget by 1.5×. | MVP |

## 8. Hardware contract

Properties of the board the firmware depends on. Changing one of these is a
firmware change, not just a hardware change — see `TIMING.md` for derivations.

| ID | Req | Status |
|---|---|---|
| HW-1 | The front end SHALL be non-inverting overall (level-shift MOSFET followed by an *inverting* Schmitt trigger, e.g. 74LVC14): lamp on → logic high. This sets the `active_low` default. | MVP |
| HW-2 | Every `DATA` net SHALL carry a ~10 kΩ pull-down **at its receiving end** — one per module on `J2.3`, plus one at the master on `MISO` — oriented so that an absent, unpopulated or unpowered upstream driver reads *lamp off*, which given HW-1 means pulled low. The MCU's internal pull on `MISO` SHALL be configured to match rather than left at the `gpio_reset_pin()` default (pull-up). HW-1, HW-2 and the internal pull are one decision. | MVP |
| HW-3 | Chain logic SHOULD be LVC family at 3.3 V, for edge rate and drive into the multi-drop `CLK` bus. `74LV165A` is an acceptable substitute; `74HC165` is acceptable at **≤ 4 MHz** and is the practical choice for a through-hole bench build. *(Relaxed from ≤ 2 MHz on 2026-08-07: 4 MHz ran clean on a 4-chip breadboard rig, 2 modules / 32 ch at 3.3 V, for millions of frames with zero read errors. The limit at longer chains is multi-drop `CLK` integrity across 800 mm, not the part — see HW-14 and `TIMING.md` §4.3 — so this ceiling is about the device, and chain length is governed separately.)* Since rev D there is no per-hop gate delay in the clock path, so family choice is no longer a chain-length correctness issue. | MVP |
| HW-4 | Modules SHALL chain on a **5-pin** JST-SH harness: `VCC` (5 V), `GND`, `DATA`, `CLK`, `/PL`, in ~100 mm hops, up to 8 modules / 800 mm. `CLK` and `/PL` are bussed; `DATA` is point-to-point and is the only signal that differs between `J1` and `J2`. | MVP |
| HW-5 | Each module SHALL carry local decoupling (100 nF per IC + ~10 µF bulk). `CLK` SHALL have 33–100 Ω series termination **at the master** (the bus source), and each module's `QH` SHALL have a 33 Ω series resistor before `J1` — source-terminating the point-to-point hop and current-limiting an output collision if a module is reversed. | MVP |
| HW-6 | pinled ground SHALL tie to the machine's lamp-return ground at a single point near the lamp matrix return. | MVP |
| HW-7 | The input SHALL survive rail sag from solenoid firing (series Schottky + bulk capacitance + kickback clamping) without an MCU brownout reset. | MVP |
| HW-8 | Distribution SHALL be 5 V on the harness with a local 3.3 V LDO on every module. LVC is not a 5 V part, so this is now required rather than preferred. Higher input rails require a single switching regulator at the controller, not per-module switchers adjacent to the sense bus. | MVP |
| HW-9 | The LED data line SHOULD be level-shifted to meet WS2812B V_IH (0.7 × VDD), or the strip run at a reduced VDD. | v1 |
| HW-10 | No analog time constant may appear anywhere in the chain. Every capture and every transfer SHALL be registered and edge- or level-defined. | MVP |
| HW-11 | The chain SHALL be **self-terminating**: a partially populated harness reads as lamps-off beyond the last fitted module, with no terminator plug, jumper or build variant (HW-2's per-module pull-down provides this). | MVP |
| HW-12 | Each module's serial output SHALL be taken from `QH`, never `/QH`. Inverting the serial output would make an absent module's pull-down read as every channel *on*, defeating HW-11. | MVP |
| HW-13 | `J1` (upstream, `DATA` = output) and `J2` (downstream, `DATA` = input) SHALL be keyed or gendered so a module cannot be fitted backwards, which would tie two push-pull outputs together. | MVP |
| HW-14 | The `CLK` bus SHALL be routed so it propagates *along* the harness, master to downstream, rather than star-wired. This keeps each module clocked before the one feeding it, so harness skew adds to the inter-device hold margin instead of eroding it (`CHAINING.md`). | MVP |

## 9. Out of scope (first cut)
- OTA / Wi-Fi provisioning UI, web config portal.
- Reverse-engineering per-title lamp tables (baseline behavior comes from
  sensing, not decoding ROM state).
- PCB/gerber design (tracked in the hardware repo, not firmware).
